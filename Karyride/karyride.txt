# KaryRide V1 — FULL APPLICATION LOGIC SPECIFICATION

## 1. SYSTEM CONCEPT

KaryRide is a **multi-company transport platform**.

It is not one taxi company.

The platform operator controls the ecosystem, while independent transport companies operate inside KaryRide.

```text
                         KARYRIDE PLATFORM
                                │
             ┌──────────────────┼──────────────────┐
             │                  │                  │
        SUPER ADMIN         COMPANIES            CLIENTS
                                │
                    ┌───────────┼───────────┐
                    │           │           │
                  STAFF       DRIVERS     VEHICLES
                                │           │
                                └─────┬─────┘
                                      │
                                  CATEGORIES
                                      │
                                   PRICING
                                      │
                                    RIDES
                                      │
                              PAYMENT / INVOICE
                                      │
                                   REVIEWS
```

The fundamental rule is:

> **KaryRide owns the platform; companies operate transport services through it.**

Companies don't control the entire platform.

They control only their own operational data.

The Super Admin is **not a transport company**.

# 3. COMPANY CREATION MODEL

This is important because of your requirement:

> **Companies are added/created by KaryRide administration.**

The public doesn't freely create an operational company and immediately start using the platform.

The workflow is:

```text
SUPER ADMIN
     ↓
Creates company
     ↓
Creates company owner account
     ↓
Provides credentials to owner
     ↓
Owner logs in
     ↓
Company completes/manages its operational information
     ↓
Super Admin controls approval/status
```

Therefore, `companies.owner_user_id` identifies the primary owner account.

# 4. AUTHENTICATION LOGIC

## Login

A user enters:

* phone or email
* password

PHP:

1. validates input
2. searches `users`
3. verifies `password_hash`
4. checks `is_active`
5. checks global ban
6. starts authenticated session
7. loads role
8. redirects to appropriate dashboard

Example:

```text
superadmin        → /admin
company_owner     → /company
company_manager   → /company
company_employee  → /company
driver            → /driver
client            → /client
```

## Global ban

If:

```text
is_banned_globally = 1
```

the account cannot use KaryRide even if its company account is active.

This is different from a company-specific restriction.

# 6. COMPANY ISOLATION

This is one of the most important KaryRide rules.

Every company user must operate inside a company context.

For example:

```text
Company A
```

must never see:

```text
Company B drivers
Company B vehicles
Company B rides
Company B promotions
Company B pricing
Company B restrictions
```

except where the platform intentionally exposes public information.

Every company-side query should effectively behave like:

```sql
WHERE company_id = CURRENT_COMPANY_ID
```

The application should **never trust a company_id sent by the browser**.

It should obtain the company from the authenticated session/user relationship.

# 12. DRIVER STATUS

Driver status:

```text
offline
available
busy
```

### Offline

Driver isn't currently accepting rides.

### Available

Driver is eligible for new ride requests.

### Busy

Driver is currently handling a ride.

The application should never send a normal new ride to:

```text
busy
offline
suspended
inactive
```

drivers.

# 13. DRIVER LOCATION

When a driver is online/available, the driver's application periodically sends:

```text
latitude
longitude
timestamp
```

to KaryRide.

The database stores:

```text
current_latitude
current_longitude
last_location_update
```

The system should consider a driver "location-valid" only if the last update isn't too old.

For example:

```text
last update recent
+
driver available
+
not suspended
+
active account
=
eligible
```

The exact timeout should be configurable later.

# 14. DRIVER ASSIGNMENT

This is the core dispatch mechanism.

Client:

```text
requests ride
```

KaryRide:

```text
find eligible drivers
```

Criteria include:

1. correct company/category
2. available
3. active
4. not suspended
5. valid recent location
6. compatible vehicle
7. within acceptable distance

Then calculate proximity.

Conceptually:

```text
client pickup
       ↓
available drivers
       ↓
distance calculation
       ↓
nearest eligible drivers
       ↓
dispatch request
```

---

# 15. DRIVER DISPATCH MODEL

For V1, use a **controlled dispatch system**, not complicated infrastructure.

A practical flow:

```text
Ride pending
     ↓
Find nearby eligible drivers
     ↓
Offer ride
     ↓
Driver accepts
     ↓
Ride becomes accepted
     ↓
Other offers become invalid
```

The critical operation must be atomic.

If two drivers attempt to accept simultaneously:

```text
Driver A accepts
Driver B accepts
```

only one may win.

The system verifies:

```text
ride.status = pending
AND driver still eligible
```

before assigning.

The first successful transaction wins.

# 20. DISTANCE CALCULATION

KaryRide calculates estimated route distance.

Conceptually:

```text
Pickup
  ↓
Routing service
  ↓
Distance
  +
Estimated duration
```

Store:

```text
estimated_distance_km
estimated_duration_min
```

Do not blindly use straight-line distance as the final fare distance when a proper route distance is available.

---

# 21. PRICE CALCULATION

Pricing comes from:

```text
pricing_plans
```

The plan contains:

```text
base_fare
price_per_km
min_fare
advance_booking_fee
```

The basic formula is:

```text
base fare
+
(distance × price per km)
=
calculated fare
```

Then:

```text
if calculated fare < minimum fare
    total = minimum fare
else
    total = calculated fare
```

Conceptually:

```text
Fare =
MAX(
    min_fare,
    base_fare + distance_km × price_per_km
)
```

This pricing logic is already described in the schema documentation. 

---

# 22. PRICE SNAPSHOT

This is extremely important.

When the ride is created, copy the pricing result into:

```text
rides.base_fare
rides.distance_fare
rides.discount_amount
rides.total_amount
```

The ride then owns its historical price.

Suppose:

```text
Today = 800 BIF/km
```

and tomorrow:

```text
1000 BIF/km
```

Yesterday's ride remains based on:

```text
800 BIF/km
```

It must not be recalculated from the current pricing plan.

# 26. DISCOUNT SAFETY

Discount cannot produce a negative fare.

For example:

```text
Original = 2,000
Discount = 3,000
```

Result:

```text
0
```

not:

```text -1,000
```

Application logic should enforce:


# 51. IMPORTANT FINANCIAL RULE

Never calculate historical company revenue using today's commission setting.

If the platform commission changes:

```text
5% → 7%
```

old rides must not suddenly become 7%.

Therefore, when the financial/accounting side becomes more advanced, the transaction should snapshot the applicable financial values.

For V1 reporting, the application can calculate from the ride/payment records while preserving historical ride pricing.

The application must prevent invalid transitions.



# 67. CONCURRENCY

This is extremely important.

Imagine:

```text
Driver A clicks ACCEPT
Driver B clicks ACCEPT
```

at almost exactly the same moment.

The backend must ensure only one succeeds.

The database transaction should verify:

```text
status = pending
```

then lock/update the ride.

Winner:

```text
accepted
```

Loser:

```text
Ride no longer available
```

This is a backend rule, not a JavaScript rule.

---

# 68. SECURITY PRINCIPLE

Never trust:

```text
company_id
driver_id
vehicle_id
client_id
price
total_amount
role
```

coming from the browser.

The server calculates/validates them.

For example, a malicious client could send:

```text
total_amount = 100
```

instead of:

```text
total_amount = 15,000
```

PHP must ignore the submitted price and calculate it from trusted database data.

---

# 69. CLIENT PRICE SECURITY

The frontend can show:

```text
Estimated: 8,500 BIF
```

but the backend recalculates/validates the price when creating the ride.

Frontend = presentation.

Backend = authority.

---

# 70. COMPANY DATA SECURITY

A request like:

```text
/company/vehicles.php?id=15
```

must not simply execute:

```sql
SELECT * FROM vehicles WHERE id = 15
```

It must verify company ownership.

Conceptually:

```sql
WHERE id = 15
AND company_id = CURRENT_COMPANY_ID
```

Same principle for:

* drivers
* vehicles
* rides
* promotions
* pricing
* restrictions
* documents

---

# 71. CLIENT DATA SECURITY

A client should only access their own:

```text
rides
invoices
reviews
profile
```

Never:

```text
another client's ride
```

---

# 72. DRIVER DATA SECURITY

Driver should only access:

* their own profile
* their own current ride
* ride requests assigned/offered to them
* operational location functions

They should not be able to manipulate another driver.

---

# 73. PASSWORD SECURITY

Passwords are never stored directly.

Only:

```text
password_hash
```

is stored.

PHP should use:

```text
password_hash()
password_verify()
```

with secure password hashing.

---

# 74. SESSION SECURITY

After login:

```text
session_start()
```

and store only necessary identity information.

For example:

```text
user_id
role
```

Company context should be derived securely from the authenticated user's relationships rather than blindly accepting a browser-supplied company ID.

Sessions should be regenerated after authentication.

Logout destroys the authenticated session.

---

# 75. CSRF

All state-changing web forms should use CSRF protection.

Especially:

```text
create company
add driver
add vehicle
change pricing
create promotion
accept ride
cancel ride
start ride
complete ride
mark payment
approve document
suspend user
```

---

# 76. INPUT VALIDATION

Every backend endpoint validates:

* required fields
* data types
* lengths
* allowed enums
* numeric ranges
* coordinates
* dates
* ownership
* permissions

Client-side validation is only for UX.

Server-side validation is mandatory.

```text
COMMIT
```

If anything fails:

# 85. DATA DELETION PHILOSOPHY

For example:


Deactivate rather than destroy historical records.


and similarly for:

```text

vehicle
```

This is an intentional pragmatic design for V1.

# 103. WHAT HAPPENS WHEN A COMPANY IS SUSPENDED?

Existing historical rides remain.

But:

```text
new bookings → blocked
drivers → cannot receive new rides
company dashboard → restricted operational actions
```

The system should handle active rides carefully rather than abruptly corrupting them.

Historical:

```text
completed rides
invoices
reviews
```

remain intact.

---

# 104. WHAT HAPPENS WHEN A DRIVER IS SUSPENDED?

Driver:

```text
is_suspended = 1
```

Then:

```text
cannot receive new rides
```

If they are currently on a ride, the system should not simply delete the ride association.

The active ride requires controlled administrative handling.

---

# 105. WHAT HAPPENS WHEN A VEHICLE IS DEACTIVATED?

Vehicle:

```text
is_active = 0
```

Then:

```text
cannot be assigned to new rides
```

Historical rides remain valid.

---

# 106. WHAT HAPPENS WHEN PRICES CHANGE?

Nothing changes for existing rides.

New booking:

```text
new pricing
```

Existing ride:

```text
stored snapshot
```

This is exactly why the pricing values are stored directly on `rides`. 

---

# 107. WHAT HAPPENS WHEN A PROMOTION EXPIRES?

It cannot be applied to new bookings.

Historical rides that already used it remain unchanged.

The ride keeps:

```text
promo_id
discount_amount
```

and therefore preserves what happened historically.

---

# 108. WHAT HAPPENS WHEN A CLIENT IS RESTRICTED?

Future bookings with that company:

```text
blocked
```

Other companies:

```text
still available
```

unless globally banned.

---

# 109. WHAT HAPPENS WHEN NO DRIVER IS FOUND?

The ride remains:

```text
pending
```

while the dispatch process searches according to configured timeout/retry rules.

Eventually:

```text
cancelled
cancelled_by = system
```

with a meaningful reason.

The client gets a clear message.

---

# 110. WHAT HAPPENS WHEN DRIVER CANCELS?

Possible:

```text
Driver cancellation
      ↓
driver becomes available
      ↓
ride returns to dispatch
```

if policy permits.

Otherwise:

```text
ride cancelled
```

The exact business policy should be configurable in application logic.

---

# 111. WHAT HAPPENS WHEN CLIENT CANCELS AFTER ACCEPTANCE?

The system evaluates:

```text
current ride state
+
cancellation policy
```

Then either:

```text
allow cancellation
```

or:

```text
reject cancellation / apply applicable fee
```

The important part is that the cancellation is recorded.

---

# 112. WHAT HAPPENS IF THE APP CLOSES?

The ride remains in the database.

When the user returns:

```text
load current active ride
```

from the backend.

The application should never rely on browser memory as the source of ride state.

---

# 113. WHAT HAPPENS IF DRIVER PHONE RESTARTS?

Driver logs back in.

Backend retrieves:

```text
current active ride
```

and restores the appropriate screen.

The server remains the source of truth.

---

# 114. WHAT HAPPENS IF CLIENT PHONE RESTARTS?

Same principle.

Client logs back in:

```text
GET active ride
```

and sees the current state.

---

# 115. SOURCE OF TRUTH

This principle should govern the whole project:

> **The MySQL database + backend are the source of truth.**

Not:

```text
JavaScript
browser
localStorage
URL parameters
```

Those are interfaces.

# 117. APPLICATION ARCHITECTURE PRINCIPLE

Because you specifically don't want the project unnecessarily spread into dozens of tiny files:

**Don't create a giant `functions.php` containing the entire application.**

At the same time, don't create:

```text
one file for every tiny function
```

Instead, each major application area should own its related logic.

For example:

```text

    → booking-related processing

driver page
    → driver operational processing

company vehicles page
    → vehicle management logic

company pricing page
    → pricing management logic

admin companies page
    → company administration logic
```

Shared infrastructure can remain genuinely shared.

The objective is:

> **compact structure without turning one file into an unmaintainable monster.**
